# Deployment

Three free services, each doing one job:

```
Browser ──HTTPS──▶ Web app (Vercel)          the pages people open
   │
   └──HTTPS /api──▶ API (Render, Docker) ───▶ Supabase: PostgreSQL + sign-in
                        │
                        ├──▶ Gmail (invitations and notifications)
                        └──▶ Gemini / Grok (handover drafts, set in the admin page)
```

| Service | What it runs | Free tier notes |
|---|---|---|
| Supabase | Database, row-level security, passwords | Pauses after 7 days with no activity; resume it in the dashboard |
| Render | The API (`backend/`, Docker) | Sleeps after 15 min idle; the first request then takes about a minute. Scheduled reminders wait while it sleeps. The paid Starter plan stays awake |
| Vercel | The web app (`frontend`) | No practical limits for this use |

> The steps below match the code and the included `render.yaml`, but this repository has not yet
> been deployed to these live services. Check each step's result before moving on.

The order matters: Supabase first, then Render (it needs the Supabase keys), then Vercel (it
needs the Render address), then Render again (it needs the Vercel address).

## 0. Put the code on GitHub

Push this repository (for example `github.com/<you>/silenthandover`). `backend/.env` and
`backend/.data/` are ignored by git, so local passwords, keys and databases are not uploaded.

## 1. Supabase — database and sign-in

1. At supabase.com create a project. Choose a region near your users (e.g. Singapore) and save the
   **database password** somewhere safe.
2. **Authentication → Sign In / Providers**: keep **Email** on, and turn **off** "Allow new users to
   sign up" (only the administrator creates accounts). Email confirmation is not used: invitations
   come from the app.
3. Copy these for Render:
   * **Connect** (top bar) → **Session pooler** connection string. Replace `[YOUR-PASSWORD]` with the
     database password. Use the Session pooler: Render cannot reach the direct (IPv6) address.
   * **Project Settings → Data API**: the Project URL.
   * **Project Settings → API Keys → Legacy API keys**: `anon` and `service_role`. The
     `service_role` key can do anything — paste it only into Render, never into the web app.
4. **Project Settings → Data API → Exposed schemas**: keep only `public` (never `app` or `internal`).

You do not create tables yourself: the API creates them on its first start.

## 2. Render — the API

1. At render.com: **New → Blueprint**, connect GitHub and pick the repository. Render reads
   `render.yaml` and asks for the values marked `sync: false`:

   | Variable | Value |
   |---|---|
   | `DATABASE_URL` | the Session pooler string from step 1 |
   | `SUPABASE_URL` | the Project URL |
   | `SUPABASE_ANON_KEY` | the `anon` key |
   | `SUPABASE_SERVICE_ROLE_KEY` | the `service_role` key |
   | `APP_BASE_URL`, `CORS_ORIGINS` | for now `https://example.com`; replaced in step 4 (no invitation is sent while it is a placeholder) |
   | `FIRST_ADMIN_EMAIL` | the IT administrator's email |
   | `GMAIL_USER` | the Gmail address that sends emails |
   | `GMAIL_APP_PASSWORD` | its 16-letter App Password |

   `SECRETS_ENCRYPTION_KEY` is generated by Render. Never change it afterwards, or the keys saved in
   the admin pages can no longer be opened.
2. Wait for the deploy, then open `https://<your-api>.onrender.com/api/health`. It should show
   `{"ok":true}`. The log shows `database migrated` on the first start.
3. Copy the API address (`https://<your-api>.onrender.com`).

## 3. Vercel — the web app

1. At vercel.com: **Add New → Project**, import the repository.
2. Set **Root Directory** to `frontend`. The included `vercel.json` builds it and sends every page to
   `index.html`.
3. **Environment Variables**: `VITE_API_URL` = the Render API address from step 2 (no trailing slash).
4. Deploy, then copy the site address (for example `https://silenthandover.vercel.app`).

## 4. Connect them, then sign in

1. On Render → the API service → **Environment**: set `APP_BASE_URL` and `CORS_ORIGINS` to the
   Vercel address, and save (Render redeploys).
2. On that start the API creates the administrator (`FIRST_ADMIN_EMAIL`) with no password and emails
   an invitation. If the email does not arrive, the API log has a line
   `FIRST ADMINISTRATOR: ... open this one-time link`. It also sends a new one after a restart if the
   last link expired without being used.
3. Open the invitation, choose a password. You are signed in as the IT administrator.
4. In the app: **Integrations** → connect the AI (Gemini key) and, optionally, the email sender
   again (it then replaces the Gmail variables). Add **Departments**, then **Users**: each
   supervisor and employee gets their own invitation email and chooses their own password.

## Alternative: your own VPS (Coolify) instead of Render and Vercel

A VPS runs all the time, so nothing sleeps. Supabase still holds the database and passwords (step 1
above); the VPS runs the API and the web app as two Docker containers, each on its own subdomain.
Apps that already run on the VPS are not affected.

1. **DNS** (where you manage your domain): add two `A` records pointing to the VPS's IP address, for
   example `handover.yourdomain` (web) and `api-handover.yourdomain` (API). Coolify issues the HTTPS
   certificates.
2. **Secrets key**: on the VPS run `openssl rand -base64 32` and keep the result. It becomes
   `SECRETS_ENCRYPTION_KEY`; never change it later.
3. **API** — Coolify → your project → **+ New → Application** → your GitHub repository:
   * Build pack **Dockerfile**, Dockerfile location `/backend/Dockerfile`, base directory `/`.
   * Port **8787**. Domain `https://api-handover.yourdomain`.
   * Environment variables: everything in the Render table in step 2, plus
     `NODE_ENV=production`, `APP_MODE=supabase`, `DEMO_MODE=false`, `AI_ADAPTER=admin`,
     `EMAIL_TRANSPORT=gmail`, `SECRETS_ENCRYPTION_KEY`, and
     `APP_BASE_URL` / `CORS_ORIGINS` = `https://handover.yourdomain`.
   * Health check path `/api/health`. Deploy; `https://api-handover.yourdomain/api/health` shows
     `{"ok":true}`.
4. **Web** — **+ New → Application**, same repository:
   * Build pack **Dockerfile**, Dockerfile location `/frontend/Dockerfile`, base directory `/`.
   * Port **80**. Domain `https://handover.yourdomain`.
   * Environment variable `VITE_API_URL=https://api-handover.yourdomain`, marked as a **build**
     variable (it is built into the pages).
5. Open the invitation emailed to `FIRST_ADMIN_EMAIL` and continue with step 4.3 above.

Without Coolify, the same two images run with plain Docker:

```bash
docker build -f backend/Dockerfile -t silent-handover-api .
docker build -f frontend/Dockerfile --build-arg VITE_API_URL=https://api-handover.yourdomain -t silent-handover-web .
docker run -d --restart unless-stopped --env-file api.env -p 127.0.0.1:8787:8787 silent-handover-api
docker run -d --restart unless-stopped -p 127.0.0.1:8080:80 silent-handover-web
```

with a reverse proxy (Caddy or nginx) giving each subdomain HTTPS and forwarding to those ports.

## Changing the code later

Push to GitHub: Vercel and Render rebuild automatically. New files in `supabase/migrations` are
applied on the API's next start (`MIGRATE_ON_START=true`, the default).

## Optional: n8n

AI, email and SMS can instead run through self-hosted n8n workflows (`AI_ADAPTER=n8n`,
`EMAIL_TRANSPORT=n8n`, `SMS_TRANSPORT=n8n`). Follow `n8n/README.md`; webhooks must use HTTPS in
production.

## Before real workplace data

* Confirm the AI provider's data-processing and retention terms in writing (see
  `docs/capstone/05-pii-sanitization-matrix.md`). Gemini's free tier may use what is sent to improve
  Google's products; names and contact details are removed first, but use a paid plan for real data.
* Record the prompt regression run (`npm run prompt:eval`) for the prompt version you deploy.
* Review `pii_retention_days`, `ai_timeout_minutes`, `escalation_hours` in admin **Settings**.
